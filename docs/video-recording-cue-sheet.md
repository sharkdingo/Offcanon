# Offcanon 视频录制逐句提示单

这份提示单按题目 PDF 的要求设计：视频不只是展示界面，而是用一次真实编程任务证明
“隔离实验 -> 可信验收 -> 用户决定是否写回”的因果链。目标时长 115-120 秒，最后
必须落在成功的 `PROMOTED`/“已应用”回执。

## 先锁定的事实

- 演示仓库：`D:\offcanon-video-demo\slug-demo`。
- 当前干净基线：`3a64963`。
- 基线命令结果：4 个测试，1 个 Unicode 用例失败；不要在视频里说成 5 个/2 个。
- Agent 按任务要求补充回归测试后，通常会得到 5 个测试全部通过；最终数字以画面中的
  实际输出为准。
- 项目已经配置验收命令时，第一次发送“新任务”会自动启动；结果封存后通常自动进入
  验收。只有状态确实停在待运行或待验收时才手动点击相应按钮。

## 录制前准备

### 1. 启动服务

如果服务尚未运行，打开两个 PowerShell 窗口。第一次安装依赖即可，录制当天不要在
 画面中执行安装或输出环境变量。

```powershell
# 窗口 A：后端
$env:JAVA_HOME = 'D:\jdk\jdk-22'
Set-Location 'D:\推免\backend'
mvn spring-boot:run

# 窗口 B：前端
Set-Location 'D:\推免\frontend'
npm run dev -- --host 127.0.0.1
```

浏览器打开 `http://127.0.0.1:5173/`。只使用回环地址；不要把服务改成公网监听。

### 2. 检查演示仓库基线

在录制前的终端预演一次，确认输出与下面一致。运行测试产生的字节码已被 `.gitignore`
 排除，不会成为演示差异。

```powershell
Set-Location 'D:\offcanon-video-demo\slug-demo'
git status --short                    # 应为空
git rev-parse --short HEAD            # 应为 3a64963
python -B -m unittest discover -s tests -v
git diff --check
```

预演时应看到 `Ran 4 tests`，并且只有 Unicode 断言失败。不要先在这个仓库手工修复或
提交；修复必须由视频中的 Agent 产生。

### 3. 在 Offcanon 登记项目

1. 顶部或侧栏点击 `打开或新建项目`（加号）。
2. 选择 `打开已有项目`。
3. `项目目录` 填入 `D:\offcanon-video-demo\slug-demo`。
4. `项目名称` 填入 `Slugify Unicode 修复演示`。
5. `项目验收命令` 每行一条，粘贴：

   ```text
   python -B -m unittest discover -s tests -v
   git diff --check
   ```

6. 点击 `打开项目`。

如果该项目已经在当前账户中，直接打开它并检查命令，不要重复登记。若项目已有旧任务，
  录制时先点击侧栏的 `新任务`，不要点旧任务的 `继续任务`。

### 4. 私下配置模型

点击 `打开设置`，填写模型 Endpoint、模型名和 API key，先点连接测试，再保存。测试
完成后关闭设置；视频全程不要打开 API key 输入框、不要展示环境变量或密钥。模型服务
 可以是用户已配置的 OpenAI 兼容端点，端点和密钥不写入仓库。

### 5. 任务提示词（完整粘贴，不要临场改写）

```text
请修复 src/slugify.py 的真实 Unicode 边界问题。当前实现会丢失中文和带重音的 Unicode 字母；例如“南京大学 2026”中的中文词不能丢失。要求：
1. 保留 Unicode 字母和数字；
2. 连续的非字母数字字符替换为一个半角连字符；
3. 结果转为小写，并去掉首尾连字符；
4. 只修改必要文件，并在 tests/test_slugify.py 中补充一个覆盖标点和下划线的回归测试；
5. 不要删除或放宽已有测试，不要修改配置文件，不要访问网络；
6. 请先读取 BUG_REPORT.md，再依次使用目录浏览、搜索、读取工具定位实现；可以先运行现有测试确认失败；完成修改后逐条运行：python -B -m unittest discover -s tests -v 和 git diff --check，并总结实际修改和检查结果。
```

## 逐秒操作与台词

录制时只照着“操作”栏点击或按键；“台词”栏按原文朗读。等待模型时保留真实活动，
 只在剪辑中加速等待，不要伪造工具调用或删除验收证据。每个关键状态至少停留 2 秒。

| 0:08-0:16 | 切到终端，展示 `BUG_REPORT.md` 或基线测试失败；只停留约 3 秒，再切回浏览器。 | 清楚看到 `Ran 4 tests`、1 个 Unicode failure，且 `git status` 为空。 | **“今天修复一个南京大学标题的 Unicode slug 边界问题，基线四个测试中有一个失败。”** |

### 自动流程的例外分支

只在录制现场真的出现对应状态时执行，不要为了“展示按钮”主动制造分支：

| 画面状态 | 额外操作 | 处理后台词 |
| --- | --- | --- |
| `READY_TO_RUN` / `启动代理` | 点击一次 `启动代理`，回到 0:24 的活动时间线。 | “任务已经准备好，现在启动隔离实验。” |
| `结果已锁定，尚未运行验收` / `运行验收` | 点击一次 `运行验收`，等待 `已通过验收`，再进入审阅。 | “封存结果仍需按项目策略验收，我现在启动可信检查。” |
| `验收未通过`、`实验运行失败` 或模型缺少设置 | 放弃这一 take；不要在成片中修补。恢复干净基线后重新录。 | 不使用此台词，不把失败状态作为主视频结尾。 |
| 应用对话框显示 `项目主线已变化` | 不点击“标记为已过期”作为主视频结尾；改用干净副本重录。 | 该分支可另录为面试备用片段。 |

## 面试留坑（只留问题，不留坏结果）

视频中只用一句话点到为止，把实现细节留给现场追问：

- **为什么隔离？** 模型可能误改或与人并发修改；快照和审阅让结果可复现、可拒绝。
- **为什么 `AGENT_COMPLETED` 不等于 `VERIFIED`？** 前者是模型工作结束，后者必须有
  封存结果上的可信命令和源完整性检查。
- **为什么要三个指纹？** 用乐观并发检查防止覆盖主线新改动；v1 保守标记 `STALE`，
  不做无把握的三方合并。
- **为什么不信 Agent 的 shell 输出？** 它只是上下文观察；验收命令在一次性工作区
  重跑，证据与结果快照绑定。
- **这是不是安全沙箱？** 不是。当前是应用级能力边界；面对不可信代码还需要容器或
  操作系统隔离和网络出口策略。
- **哪些部分是自研？** 模型响应解析、工具注册与本地执行、重试/步数/超时、上下文
  预算、状态机、证据和晋级日志；没有使用 LangChain、Agents SDK 等 Agent 框架。
- **如果会话 A 还在运行，会话 B 先应用怎么办？** A 的实验区不受直接影响；A 以后
  应用时发现基线指纹与当前主线不同，会被标记 `STALE`，不能覆盖 B 的改动；继续任务
  会从最新主线重新建立实验，旧记录仍可审计。

## 导出前检查

- 视频为 MP4，时长不超过 120 秒，文件小于 200 MB。
- `AGENT_COMPLETED`/封存、`VERIFIED`、三个指纹、`PROMOTED` 回执都能读清。
- 画面没有 API key、环境变量、聊天通知、个人路径以外的隐私或无关窗口。
- 录制确实来自一次真实 Agent 运行；没有手工预先修改实验结果，也没有伪造时间线。
- 结尾台词准确说明：运行阶段工具只能写实验区，用户确认后由应用服务受保护地写回主线；
  应用级隔离不等于操作系统安全沙箱。
